## The row that just closed: `rve-tail-csc-yuv-2026-11-20`

`docs/wsp/verified/int8-tail-csc.txt` is the record; here is only what a successor needs.

- `tail_int8_yuv_kernel` (`backend/src/pytorch/Int8Kernels.py`) writes packed yuv420p from the tail epilogue:
  Y/Cb/Cr are linear in RGB, and the residual adds one value per position because it adds the same LR pixel to
  all four subpixels. 6 bytes per input pixel, no `cat()`, no second pass.
- `Int8Body.out_yuv` (gated on `tail_yuv` **and** the upscaler's `yuv8_output`, i.e. the same flag that chose the
  pipe format) makes `__call__` return the flat uint8 payload rather than an RGB tensor.
- `Frame._is_raw_payload` / `_raw_payload_bytes` / `_convert_payload` / `raw_payload_preview`: the pack copies
  instead of converting; `RenderVideo._calibrate_gate` takes luma from the Y plane and `_preview_bytes` decodes a
  preview. Tests: `harness/tests/test_pinned_payload.py` (5 new cases, 37 in the file).
- **Attribution, learned the hard way:** the isolated probe said the fused kernel was 0.87 against ~1.0, but in
  the app the tail phase is a **wash** (1.00 -> 1.00) and the entire -2.16 ms is YCbCr arithmetic leaving the
  pack (4.37 -> 2.06). An isolated arm that contains the conversion is not the same object as the phase lines.
- **Safety coupling is load-bearing now:** no `cat()` means no incidental synchronisation, so
  `RVE_PAYLOAD_GUARD=1` is mandatory on this path, not a free knob.

## The fp16 comparator, measured by its own layers (`fp16-engine-layers.txt`)

`trtexec 10.12.0.36` was installed without root (`~/.local/bin/trtexec`, the `libnvinfer-bin` .deb from the CUDA
ubuntu2204 repo, `LD_LIBRARY_PATH` on the app's own `tensorrt_libs`). The app's `.engine` is a TorchScript archive,
so it cannot be loaded by trtexec; the profile is of the same model exported to ONNX at 1920x1080.

- **The build level is worth 30.8 ms per frame.** Same ONNX, same card, one field different: level 3 gives 60
  layers and 78.33 ms because each of the 17 PReLUs is its own pass (35.47 ms of read-modify-write); level 5 gives
  25 layers and 47.50 ms. Build time 132.96 -> 280.72 s. The repo has defaulted to 5 since `c33dd7db`; the
  installed 2.4.2 build predates it and still ships 3.
- **The opt-5 graph is 97.7% conv**: 16 hops 40.58 (85.4%), first conv 2.19, tail 1.63, head 1.10,
  shuffle+residual 0.92, copies 0.69 (1.5%), resize 0.30. TRT already fused PReLU, the shuffle and the residual,
  so there is nothing left to fuse in the fp16 arm - the int8 win is arithmetic, and the fp16 comparator is not fat.
- The 26.1 ms body against 46.4 ms of engine layers is **not** a ratio: different instruments. The same-instrument
  ratio stays 1.665x (JC013).

## TensorRT's own int8, calibrated (`trt-int8-calibrated.txt`)

Three engines from one ONNX at builder level 5, calibration on eight named bluray frames (sha256 in the manifest),
profiled by the same trtexec: **fp16 46.854 ms in 25 layers, both int8 arms 38.87 ms in 60 layers - 1.205x**. The
layer split from 25 to 60 is the mechanism: the per-channel PReLU cannot join an int8 epilogue, so every hop pays a
boundary again (same as the Q/DQ build). Entropy and min-max agree within 0.008 ms.

Picture on held-out frames: the bright csm frame is clean (max 5.85 codes, 0.0000% above 8, 51.57 dB); the dark
violet frame is not (entropy max 91.14, **1.0715% above 8 codes**, 39.34 dB; min-max max 20.86, 0.0136%, 44.95 dB).
The failing pixels are shadows lifted by ~0.3 across the whole frame - symmetric-only quantisation plus sixteen
PReLU boundaries. Same-instrument run (one process, one input, three arms, same event bracket): **fp16 48.401, TRT int8 38.814,
Triton body 27.051 ms - the body is 1.435x faster than TensorRT's int8** and 1.789x faster than fp16; pictures
against the same fp16 reference: bright frame 5.79 vs 5.85 codes (body 1.7 dB lower), dark frame **0.0089% vs
1.0715%** above 8 codes and 49.36 vs 39.34 dB. Model scope - no tiling, no pack, both arms whole-frame.
Against the lane's bar (0.1%) the body reads 0.00125% over 494 frames, so the hand body is both
faster and three orders of magnitude better on the picture. **Do not re-run the 494-frame pair for this**: one
held-out frame is already two orders past the difference.

## What is closed, and why - do not re-run these

| family | result | why (mechanism) |
|---|---|---|
| tap reuse / smem staging / megakernel | 30 configs, all lost | **staging does not reduce LSU instructions, it adds them** (9 -> 11.26 at a 2-D tile, 9 -> 15.09 for a 3-row band), and LSU is the busiest pipe (73.9% of issue slots, 22.7% of all instructions). `tl.gather` costs 13.5x (mma makes spatial neighbours inter-lane); a register-local dp4a roofs at 44.2 TOPS against the 103.4 we already reach |
| Winograd F(2,3) | arithmetic only | the hop sits ON the ridge (610 FLOP/B measured, 611 roof); unfused Winograd trades 5x traffic for 2.13x less arithmetic |
| 2-hop cascade | dropped | the launch constant does not exist (a whole 256x256 hop is 0.0572 ms, so any per-launch fee <= 0.011 ms); traffic removal is worth ~0 when DRAM runs at 56% |
| IO pipeline overlap (streams) | -0.01 ms | the pack was **YCbCr arithmetic, not a copy** - and the tail-CSC row removed that arithmetic instead (4.37 -> 2.06) |
| pack ring (pinned slots) | -0.04 ms | same reason; ring removes `tobytes`, not the conversion. It stays available (`RVE_PACK_RING=1`) and now copies a payload |
| 6-bit codes | 2.71% of pixels against a 0.1% bar | picture |
| epilogue divide fold | -0.06..-0.66, unresolved | never measured against the MODEL; would need that check to adopt |
| M x 2 batching | +0.3%, codes differed | per-row index cost grows with rows, the constant does not shrink |
| output-channel split, 2-D tiles, cache policies, persistent CTA, reverse traversal | -3% to -176% | all schedule knobs around the same nine gathers |
| frame skipping / static regions / duplicate frames | **FORBIDDEN** by owner | `rve-reuse-gate-forbidden` |
| model cuts (fewer channels/hops, 4-bit, distillation) | 14-37% per-layer residual, 1.58% of pixels over the bar | measured |

## Invariants this lane established

- **The bar is a RATIO (`fp16 / int8`)**, so a body-side millisecond is worth ~2.8x a millisecond both arms pay.
  `FRAME-BUDGET.md` prints both columns from records.
- **Resolve every claim from the record store; never type a number into a claims block.** `harness.cli check`
  caught hand-typed values twice in one session.
- **Byte-identity pairs cannot detect a defect both arms share.** The tail-CSC pair is different-arithmetic and
  was judged on the 0.1%/8-level statistic (0.00000%, peak 6), not on identity.
- **An isolated probe that bundles the conversion is not the phase it claims to replace.** Read the app's own
  phase lines before attributing a saving.
- Copy-bench numbers are only comparable within a session; the same arm has read 1.504 to 1.595 ms across them.
