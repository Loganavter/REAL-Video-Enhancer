## The one thing in flight: `rve-tail-csc-yuv-2026-11-20`

**Done** (records `int8-tail-csc.jsonl` N001-N003, doc `int8-tail-csc.txt`):

- `tail_int8_yuv_kernel` in `backend/src/pytorch/Int8Kernels.py` writes packed yuv420p straight from the tail's
  epilogue. Y/Cb/Cr are linear in RGB, so each is a weighted sum over the channel axis of the reshaped tile; the
  residual adds one value per position because it adds the same LR pixel to all four subpixels.
- Offline gate before any kernel: both orders from the SAME tail output agree with **max |delta| 1 level** over
  the 12 441 600-byte payload (4.6% of bytes off by one, 0.00000% off by more). So it is **different-arithmetic** -
  judge it on a render pair, not on byte-identity.
- Isolated, conversion inside each arm: **5.123 ms -> 0.869 ms** (N001, N002).
- In-app expectation: tail 1.00 -> ~0.87, pack 4.36 -> ~2.0, loop ~33.58 -> ~31.2, ratio ~1.67.

**Next** (the integration, not yet started):

1. `Int8Body.__call__` must hand back a `uint8` CUDA buffer already in yuv420p layout (6 bytes per input pixel:
   four Y planes interleaved into 2H x 2W, then U, then V) instead of the fp16 RGB tensor, behind e.g.
   `RVE_TAIL_YUV=1`.
2. `Frame.get_frame_bytes` needs a branch: if the tensor is already a yuv420p byte buffer, **copy** it (pinned

## Invariants this session established

- **The bar is a RATIO (`fp16 / int8`)**, so a body-side millisecond is worth ~2.8x a millisecond both arms pay
  (`FRAME-BUDGET.md`, "Which side of the ratio"). Do not report the two as interchangeable.
- **Resolve every claim from the record store; never type a number into a claims block.** `harness.cli check`
  caught two hand-typed values this session, and three of the outside reader's five errors were manual derivations
  over someone else's measurements.

  configurations that both use the same payload path; a race there would be invisible. The guard test that DID
  check it (guard off vs on) read IDENTITY, and the guard stays on anyway because it costs 0.00 ms.
