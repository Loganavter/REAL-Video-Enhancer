# PRelu as `a*x + (1-a)*relu(x)`: the int8 boundary stops costing, and the cost moves to fp16 and Q/DQ

Measured 2026-11-19/20 (local), RTX 4060 Ti 16 GB, TensorRT **10.12.0.36** (the app's own version), builder
level 5, implicit int8 with `IInt8MinMaxCalibrator` over the lane's own eight calibration frames (the ones
`trt-int8-calibrated.txt` uses), and explicit Q/DQ built by `harness/scripts/make_qdq.py` (`--activation qint8`).
Records: `records/prelu-form.jsonl`; scratch artifacts (engines, ONNX, scripts): `/tmp/opencode/prelu-exp/`.

## The question

`trt-int8-calibrated.txt` and `engine-int8.txt` close the int8 lane on the boundary: "a per-channel PRelu
cannot join an int8 epilogue, so every hop pays a full-precision pass". PRelu is positive-homogeneous
(`PReLU(c*x) = c*PReLU(x)` for any `c > 0`), so the dequantise commutes through it and the boundary is a
**graph-form** question rather than an arithmetic one. Test: rewrite the 17 PRelus as
`a*x + (1-a)*relu(x)`, with `a` and `1-a` as constants of the slope's own `[64,1,1]` shape (no new weight
tensors, no kernel, no plugin), and rebuild.

## What the graph does

Futsuu, 1x3x1080x1920, the same builder settings for every arm:

| arm | layers | PWN (passes outside int8) | myelin | reformat | ms |
|---|---|---|---|---|---|
| fp16, as-is | 25 | 0 | **20** | 2 | 53.65 |
| fp16, rewritten | 98 | 4 | 0 | 39 | 63.40 |
| int8 min-max, as-is | 78 | **19** | 0 | 21 | 45.22 |
| int8 min-max, rewritten | 95 | **4** | 0 | 36 | **33.71** |

No arm fuses the activation into the convolution epilogue, in either precision. The mechanism is different
and simpler: **the PRelu as an operator leaves int8** (19 full-precision pointwise passes), and the
decomposed form is a scale layer that stays in int8 (4). The layer count is not the predictor - 95 layers
beat 78, while 98 lose to 25 - the predictor is how many passes leave int8.

## Speed, one instrument, one session

| arm | 1080p Futsuu | 1080p Ani4K | 4K geometry |
|---|---|---|---|
| fp16 | 53.65 | 50.68-51.48 | 205.26-206.13 |
| int8 as-is | 45.22 | 41.29 | 165.93 |
| int8 rewritten | **33.71** | **31.57** | **124.65** |
| rewrite / baseline | **1.341x** | **1.308x** | **1.331x** |
| rewrite / fp16 | 1.599x | 1.606x | 1.650x |

Interleaved rounds, engines cached, medians of rounds 2+ (within-arm spread <2%). Q/DQ, same model:

| arm | ms |
|---|---|
| explicit Q/DQ as-is | 67.4-69.2 |
| explicit Q/DQ rewritten | **141.6-145.5** (0.47x) |

The Q/DQ baseline reproduces `engine-int8.txt`'s recorded 64.3-70.4 ms, so that arm measures the
configuration E9' measured. The rewrite adds float ops *between* declared Q/DQ pairs, and there the
boundaries are declared by the graph rather than chosen by the builder, so nothing can absorb them.

The picture direction is **model-specific**: better on Futsuu, worse on Ani4K. Both stay inside the bar in
every row, so this is a margin change and not a violation, but "equal or better" is a Futsuu statement.

**4K population caveat.** The library has no native 4K cut (`sources.yaml` holds 1080p BDRemux copies and a
1440x1080 one), so the 4K input frames are the same 1080p frames upscaled 2x with lanczos. That input is
smoother than real 4K, which is why the 4K shares are ~100x smaller: the row tests the **engine geometry**
(tactic set and fusion change with the shape), not a 4K picture, and it is not comparable to the 1080p row.

## The app path: the plan loads and the win is 1.25x at the product level

The app has a TensorRT path that takes a prebuilt plan: `TensorRTHandler.load_engine` returns
`RawTRTEngine(<engine>.plan)` when `RVE_RAW_TRT=1` and that file exists, with no code change. Both int8 plans
above were therefore dropped in as `<engine>.plan` for the same engine name and rendered by the app itself
(`backend/rve-backend.py`, `--output null`, reuse off), the plan swapped between arms inside one session so the
drift is common to both, 52 frames of `bd_violet20s`:

| arm | round 1 | round 2 | median |
|---|---|---|---|
| int8 as-is | 48.91 | 49.24 | **49.08 ms/frame** |
| int8 rewritten | 39.40 | 39.07 | **39.24 ms/frame** |

**1.251x in the render loop** against 1.341x on the engine - the difference is pack + queue and read wait,
which both arms pay. Lossless ffv1 pair of the same 52 frames, `gate_sweep --reference-kind config`:
**worst share 0.01767% (frame 30), 0 of 52 frames above the 0.1% bar, worst block mean 2.64, peak 18** - the
app-level picture moves the same way as the engine-level one, far inside the bar.

## Calibrator and fp16 controls

- **entropy calibrator**: both arms fail on Violet (3.03037% against 2.99672% worst, 13 of 16 frames over
  the bar, peaks 86/85). The calibrator decides that, not the form.
- **fp16**: rewritten fp16 against original fp16 is **0.00000%, peak 1** on Futsuu and Ani4K, i.e. the same
  function up to rounding. On Futsuu the rewrite then costs 18% (it destroys the 20 myelin Conv+PReLU
  blocks); on Ani4K fp16 keeps all 19 blocks and the rewrite is time-neutral. So the fp16 cost is
  model-specific too.
- **A/A**: fp16 against itself, 0.00000% / peak 0.

## Two traps this run walked into

1. The first variant was `x + (a-1)*relu(x)`, which is **not** PRelu (for `x < 0` it returns `x`, not
   `a*x`). It built without complaint and looked 25% faster; the fp16 control read **100.00000%** of pixels
   off with peak 126-227, which is what identified the error as algebra rather than quantisation.
2. `harness/scripts/build_plan.py --parse` sets only `BuilderFlag.FP16`, and a Q/DQ plan built through it read
   133-135 ms against 68 ms for the same graph built with `BuilderFlag.INT8`. **The flag is not the cause**,
   and this was measured rather than assumed: two builds of the identical `qdq_base.onnx` with
   `EXPLICIT_BATCH`, opt 5 and 8 timing iterations, differing only in the INT8 flag, read **73.48 / 69.80**
   (flag on) and **69.76 / 71.72** (flag off), 83 and 82 layers, and the flag-off plan's picture against the
   fp16 engine is the same 0.000% / peak 7.43. So int8 on a Q/DQ graph comes from the Q/DQ nodes, as
   `harness/harness/scripts/probe_int8_tactics.py` says. The 133 ms plan is an outlier whose cause is not established - the
   build took 468 s against 450 s here and ran while other work was on the card, which is the documented way
   a builder picks worse tactics (`avg_timing_iterations` measures under whatever load is present).

## What this changes in the record

- The int8 boundary tax on this activation is **removable by graph expression on the implicit-int8 path**;
  the lane's own hand-written body (1.665x end-to-end) is within 4% of what a 30-line ONNX rewrite gives
  (1.599x at 1080p, 1.650x at 4K).
- The lever is **mode- and model-specific**: it costs 18% on Futsuu fp16, is fp16-neutral on Ani4K, and is
  2.1x worse under explicit Q/DQ. `E9'` stands: the Q/DQ route is not fixed by this form.
- Not checked: a native-4K picture (the 4K row's population is 1080p upscaled with lanczos), NVENC, and a
  second card.

## Reproduce

```bash
# the rewrite (both directions, algebra exact): PRelu -> a*x + (1-a)*relu(x)
python3 rewrite_prelu.py futsuu.onnx out/            # out/futsuu_mul_relu.onnx
# engines: fp16 + implicit int8 min-max, same 8 frames, same builder
python3 harness/scripts/trt_int8_calibrate.py --onnx out/futsuu_mul_relu.onnx \
    --frames <8 rgb frames> --out out/a --arms fp16,int8-minmax
# picture: 16 held-out frames against the fp16 engine of the unmodified ONNX
python3 compare_and_time.py ref=<fp16.plan> base_i8=<as-is.plan> a_i8=<rewrite.plan>
# Q/DQ: the same form over a Q/DQ graph, with INT8 enabled (build_plan.py sets only FP16)
python3 harness/scripts/make_qdq.py <model.pth> futsuu.onnx out/qdq.onnx --frames <dir> --activation qint8
python3 build_int8qdq.py out/qdq.onnx out/qdq.plan
```

Scratch scripts and engines: `/tmp/opencode/prelu-exp/` (`RESULT.md` is the same content plus the raw round
lists). The queue row is `rve-prelu-form-int8-2026-11-20`.
