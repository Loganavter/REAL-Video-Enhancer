# Tail layout: the conv is 2.5x faster, the body loses 2.6 ms, and the wall clock only shows it on one clip

Measured 2026-11-19, two variants of the SAME configuration alternating inside one session
(`ARMS="nchw nhwc"`, `RVE_TAIL_NHWC=0/1`), three rounds per clip, null sink, BD Violet (494 frames) and the
Chainsaw same-shot cut (539). Logs: `docs/wsp/verified/logs/tail-layout-ab/`.

Why this run exists: the earlier claim - the tail conv's input memory format is worth 2.5x - was measured by
comparing two *different sessions*, which the protocol forbids for timing. This is the same comparison with
the variants interleaved, so drift lands on both.

## The phase counter sees it clearly

| clip | arm | dequant | conv | shuffle | residual | tail | body |
|---|---|---|---|---|---|---|---|
| Violet | nchw | 1.60-1.61 | **4.84-4.87** | 0.40 | 0.92-1.00 | 7.81-7.83 | 38.8 / 44.9 |
| Violet | nhwc | 1.57-1.60 | **2.33-2.40** | 0.80 | 0.89-1.55 | 5.66-6.31 | 41.3 / 41.7 |
| Chainsaw | nchw | 1.61-1.63 | **4.80-4.87** | 0.39-0.40 | 0.93-0.94 | 7.74-7.82 | 40.2 / 40.4 |
| Chainsaw | nhwc | 1.58-1.59 | **2.29-2.43** | 0.78-1.05 | 0.90-1.15 | 5.69-5.90 | 37.6 / 37.7 |

- **The tail conv drops from ~4.85 to ~2.35 ms** on both clips, in every round, which is the isolated
  probe's 5.296 -> 2.098 reproduced inside the app.
- **The shuffle pays for it** (0.39-0.40 -> 0.78-1.05 ms) because the conv now returns a channels_last
  tensor; the residual is unchanged. Net tail: **-2.0 to -2.2 ms**.
- Body median on Chainsaw, rounds 2-3: **40.3 -> 37.65 ms** (-2.65).

## The render loop sees it on one clip and not the other

| clip | nchw medians (r2, r3) | nhwc medians (r2, r3) | ratio |
|---|---|---|---|
| Chainsaw | 47.28 / 46.92 -> **47.10** | 44.69 / 44.67 -> **44.68** | **1.054x** |
| Violet | 49.00 / 45.74 -> 47.37 | 46.54 / 47.71 -> 47.13 | 1.005x |

Violet does not resolve it, and the reason is in the same table: the hops drifted 25-30 ms across those
rounds, which is larger than the effect. One Violet `nchw` round is also visibly disturbed (dequant 2.81,
conv 7.15 against 1.6 and 4.85), and the run header names the cause: **`# load_avg 4.57`** for that round
against 1.45 for its neighbour, with the same clocks (2790 MHz) - a CPU neighbour, not a property of the arm.

So: **the tail gain is real and repeated; the wall-clock confirmation exists on one clip at n=2 and does not
on the other.** This file does not claim a ratio against fp16 - the fp16 arm was not in this session by
design (the two arms were the two variants). A ratio claim needs its own session.

## Picture: bit-identical, after the calibration fix

Two lossless ffv1 renders of the SAME configuration differing only in `RVE_TAIL_NHWC`, one session, then
`gate_sweep --reference-kind config`:

```
494 frames, block 64
worst share 0.00000% (frame 0), frames above 0.1%: 0
worst block mean 0.00, peak 0
IDENTITY: every frame is bit-identical between the two files
```

So the change moves passes, not arithmetic: the view is a layout, and cudnn computed the same numbers through
it. That is the criterion the lane set for a fusion (`byte-identity only for the variant that keeps the
algorithm`, arXiv:2609.00363), and it is met.

The same identity had been measured before the calibration ordering fix; re-confirming it afterwards was not
optional, because the fix changed which frames the body calibrates on and therefore the baseline.

## The lane ratio, taken once (both arms in one session)

The change's own acceptance is the picture above. The ratio is a lane-level number and was re-taken here only
because this change is material against the 2.50 ms gap to `bar_int8_wall` (>2 ms of frame), not per-change
policy (`docs/PLAN-int8-envelope-2026-11-19.md` §7).

| clip | fp16 median r2-3 | int8 (NHWC) median r2-3 | ratio | per-round |
|---|---|---|---|---|
| Chainsaw same-shot | 56.22 ms | 45.70 ms | **1.230x** | 1.255 (r2) / 1.204 (r3) |
| Violet BD | 58.54 | 47.96 | **1.221x** | 1.267 (r2) / 1.178 (r3) |

**Both medians clear `bar_int8_wall` = 1.2x**, which the lane did not before (1.088-1.141x). The honest
caveat: one round of one clip is below the bar (Violet r3, 1.178), so the claim is "1.22-1.23x by the bar's
own statistic (median)", not "above 1.2 in every round". And this is one session on one card; the recorded
range from `int8-wall-ab.txt` (1.088-1.141) shows what session drift does to a single draw.

## Not covered

- n=2 per arm per clip after dropping round 1 in the variant A/B, so that loop comparison is weak by
  construction - which is why the ratio above comes from its own session, not from it.
- The shuffle regression is measured, not explained: the conv's output format follows its input's, so the
  shuffle and the residual now read channels_last. A conv that returns NCHW would trade 0.4 ms of shuffle
  for a copy; not tried.
- One card, one model, 1080p LR.

## Reproduce

```bash
ARMS="nchw nhwc" ARM_ENV_NCHW="RVE_TAIL_NHWC=0" ARM_ENV_NHWC="RVE_TAIL_NHWC=1" \
  CLIPS="bd_violet20s.mkv bd_csm_same.mkv" ROUNDS=3 SINK=null LOGDIR=<dir> scripts/wall_ab.sh
PYTHONPATH=scripts python3 scripts/tail_split.py --logs docs/wsp/verified/logs/tail-layout-ab
```

Run: PYTHONPATH=scripts python3 -m harness.cli check docs/wsp/verified/int8-tail-layout.txt \
