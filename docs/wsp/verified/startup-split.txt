# Start-up: 33.15 s to the first upscaled frame, and 24 of it is one block

Measured 2026-11-20, one cold backend process, BD Violet, 1920x1080, int8 arm, null sink, opt-5 tiling-full
engine, **calibration cache miss** (16 frames measured). Records `startup-split.jsonl` (ST001-ST004), raw
`logs/startup-timed.log` - the app's own stdout with every line stamped with seconds since process start.

The question this answers is the one that comes back every few weeks: "what are the ~20 seconds before upscaling
starts?" The app prints one line about it ("startup: first frame enqueued 33.15 s after process start") and never
says where the time went. Now it does.

| block | seconds | what is inside |
|---|---|---|
| **total to the first enqueued frame** | **33.15** | |
| interpreter, CLI, ffprobe, CUDA init | 2.39 | process start -> model load begins |
| **engine deserialize + the int8 probe's 16 calibration frames** | **23.89** | the block that is "the 20 seconds" |
| Triton JIT + 24 calibration frames + first body call | 6.56 | `model-call 6603.90 ms` in the host timeline |

So it is not one 20-second mystery: it is a 24-second block (the probe) and a 6.6-second block (the body's first
call, i.e. Triton compiling its kernels), on top of 2.4 s of interpreter and ffprobe.

## What each block is, and what moves it

- **23.89 s - the probe.** It decodes 16 frames and measures per-layer scales so the int8 body can run on this
  video at all. Standalone this was recorded as **29.30 s** (`int8-probe-cost-2026-11-19.txt`), and the certificate
  that used to ride on it added 33.4 s more (`int8-certificate-removal.txt` - withdrawn, and withdrawing it
  changed the picture, not just the clock). With a **calibration cache hit** the frames half disappears: the same
  configuration then reads 28.48 s in total against 26.6 s for the fp16 arm, i.e. the int8 premium is ~1.9 s
  (`REVIEW-int8-grid-k-predictor.md` section 7, a different session - the comparison is same-instrument but not
  same-day).
- **6.56 s - the body's first call.** Not inference: the host timeline shows `model-call 6603.90 ms` and the next
  frame is normal, so this is Triton compiling the head/hop/tail kernels for this shape and precision. It is paid
  once per process per shape.
- **2.39 s - the interpreter.** Imports of torch, torch_tensorrt and the backend, plus ffprobe on the input.

## What is NOT claimed

- **The 23.89 s is not split further** between the engine deserialize and the 16-frame calibration: the app prints
  one line for both. Splitting it needs a marker inside `TensorRTHandler.load_engine` or the probe, which is a
  logging change, not a measurement one.
- **The cache-miss case is the one measured here.** A warm cache is the common case for a re-render and is quoted
  from the earlier session, not re-measured today.
- **Nothing here is a frame-time result.** Start-up is paid once; the lane's ratios are all loop-time.

## Reproduce

```bash
python3 /tmp/opencode/timed_run.py > /tmp/opencode/startup_timed.log     # the same command wall_ab runs, stamped
PYTHONPATH=. python3 harness/scripts/startup_split_records.py --log /tmp/opencode/startup_timed.log
PYTHONPATH=. python3 -m harness.cli check docs/wsp/verified/startup-split.txt \
    --records docs/wsp/verified/records/startup-split.jsonl --bars docs/claims-bars.json
```
