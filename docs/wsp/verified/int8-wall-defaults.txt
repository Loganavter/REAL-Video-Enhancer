# The product ratio on today's default: 1.40x on Violet, 1.48x on Chainsaw

Measured 2026-11-20 (local), RTX 4060 Ti, the SHIPPED int8 default (fused head kernel + 16 int8 hops + int8
tail kernel), fp16 TensorRT engine against it, interleaved arms inside one session, null sink, reuse off,
3 rounds per clip, both BD cuts.
Records: `int8-wall-defaults.jsonl`; logs: `logs/wall-defaults/null/`.

This is the debt row `rve-bar-int8-wall-retake-2026-11-20`: the recorded `bar_int8_wall` claim still cites the
frame the int8 path had **before** 2026-11-20, i.e. 47.96 ms and ~1.2x. Two changes were adopted since (the
head as one kernel, -5.27 ms; the tail as a 17th int8 hop, -3.16 ms), so the number that gets quoted described
a build that no longer exists. Nothing here edits the bar: the bar is a threshold, this is the measurement.

## The numbers

| clip | arm | r1 | r2 | r3 | median r2+ |
|---|---|---|---|---|---|
| bd_violet20s (494) | fp16 engine | 56.96 | 58.71 | 53.27 | **55.99** |
| bd_violet20s (494) | int8 default | 40.46 | 41.02 | 39.00 | **40.01** |
| bd_csm_same (539) | fp16 engine | *timeout* | 52.16 | 52.18 | **52.17** |
| bd_csm_same (539) | int8 default | 35.37 | 35.27 | 35.17 | **35.22** |

**Ratios: 1.399x (Violet) and 1.481x (Chainsaw)**, against `bar_int8_wall` = 1.2x. Per-round ratios on Violet
are 1.431 and 1.366, so the median is not carrying a lucky draw.

The phase counter on the same runs (Chainsaw, median of rounds 2+): head **0.70**, quantise **0.00**, hops
**25.35**, tail **2.60**, body **28.55** - i.e. the frame is now 25.4 of 28.6 body, and the two boundary
kernels together are 3.3 ms.

## What is not clean about it

- **`bd_csm_same_fp16_r1` has no loop line**: it was killed by the script's own 1800 s timeout at frame 281 of
  539, after ~27 minutes at "FPS: 0". The arm's rounds 2 and 3 are 52.16 and 52.18 ms - reproducible to
  0.02 ms - so the median stands, but the first draw of that arm is missing for a reason that is NOT
  explained here: either the engine rebuilt a plan for this clip or the machine stalled. It is recorded rather
  than smoothed over, and it is why the row's ratio for that clip rests on two draws.
- The Violet fp16 arm shows a real spread across rounds (53.27-58.71, 10%), which is the drift the protocol
  warns about: the median is the statistic precisely because a single draw is not.
- **Null sink.** The row asked for an NVENC arm too, on the argument that the encoder moves this class of loop
  by ~10 ms. That arm was NOT run in this pass; until it is, this file measures the ratio of the pipeline
  without the encoder, and the product number under NVENC stays unquoted.

## What this changes in the record

`bar_int8_wall` = 1.2x is now cleared by **0.20x on the tighter clip and 0.28x on the other**, in the shipped
configuration, in one session. Any earlier "1.2x" or "1.088-1.141x" statement in the corpus describes a
different build (the wall-ab row of 2026-11-19 predates both adoptions) and should be read as history, not as
the current product figure.
