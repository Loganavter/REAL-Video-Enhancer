# The preview channel: what a thumbnail costs, and what it replaced

The preview used to be the output frame itself: `Frame.raw_payload_preview` cast the packed
payload to float, ran the BT.709 matrix over all 8.3 Mpx and transferred a full 4K picture
(24.9 MB) to the host **on every frame**, and the GUI then shrank it to a ~600 px label with
a nearest-neighbour scale. It is now a 640x360 thumbnail sampled in the tensor (0.35 MB from
the int8 body's payload, 0.69 MB from an RGB tensor), published only when the viewer
consumed the last one, and transferred one frame late through a pinned buffer so the loop
never waits for the device.

Read the records, not this paragraph: every number below is a record id, and
`docs/wsp/verified/records/preview-cost.jsonl` is truth. Session `s-2026-11-20T18:20+03`,
RTX 4060 Ti 16 GB, one GPU job at a time, `bd_violet120s` = 118 frames of 1920x1080 -> 4K.

## What the numbers say, and what they do not

* The removed implementation cost **PV007** per frame, the replacement **PV008** - same frame,
  same card, same session, medians of 8 calls. The ratio between them is not a record: it is a
  ratio between two records of the same unit, instrument and population.
* In the loop the int8 body's arm reads **PV001** (mean over all frames), **PV002** (median of
  the published thumbnails), **PV003** (their maximum); the fp16 arm reads **PV004**,
  **PV005**, **PV006**.
* **PV006 / PV009 is the honest limit of this change.** The variance is the host: a bare
  `rgb_planes` call - no preview code around it - reaches **PV009**'s maximum while its own
  median in the same run is 0.061 ms, and the model's wall clock for a single configuration
  swung 35.9-53.1 ms across runs. No per-frame CUDA step can carry a hard maximum on this box;
  what this change removed is the *wait*, which is why the median is stable and the transfer
  no longer sits inside the frame.

## Live proof (the window half)

The reader on a leased X display (`:91`, `live-lease`, never the desktop), a real `QLabel`
painted from a real render publishing into the same block:
`docs/wsp/verified/logs/preview-2026-11-20/live-window-640x360.png` and the reader's own
output beside it. Ten frames arrived (the render built ten thumbnails in 28 frames at the
viewer's cadence), the label and the grab are 640x360, the centre pixel reads 238,223,211 and
a 64x64 sample holds 1679 distinct colours - a picture, not a blank, black or torn frame.
What that run also caught: the int8 arm had produced *zero* thumbnails since the output
offsets were taken from the source Y plane instead of the thumbnail's, which the 8x6 unit
fixture could not see (source size == thumbnail size there). The regression test now uses a
frame four times wider than the thumbnail.

## What this does not cover

* One card, one host, one clip, one model. The tail belongs to this desktop (the same clients
  the project's performance notes name); another host may have none of it.
* The viewer is `harness/scripts/preview_sink.py`, not the Qt window: the reader's own cost
  (one 0.35-0.69 MB copy plus the YUV matrix at 0.23 Mpx, on the GUI thread) is not measured
  here. What is measured is what the render loop pays.
* Picture: the thumbnail is a preview, not an acceptance artefact - it samples one row and
  one column in six, and nothing here says it is faithful.
