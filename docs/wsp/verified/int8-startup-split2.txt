# The 6.6 s block, split: 6.2 of it was the 24 frames, and Triton costs 2.53 s only on a cold cache

Measured 2026-11-20, Futsuu at 1920x1080. Records `int8-startup-split2.jsonl` (BB001-BB004, CP005-CP007), raw
`logs/body-build-warm.json`, `logs/body-build-split.json`, `logs/cert-picture/`.

`startup-split.txt` left one line unsplit - "Triton JIT + 24 calibration frames + first body call, 6.56 s" - and a
line that is not split is the question coming back. This page splits it, and then answers the same question for
the certificate, whose 0.45% picture difference was left with two candidate mechanisms.

## The body block, by phase

| phase | time | note |
|---|---|---|
| calibration, 8 frames, 4 crops each, cache disabled | **0.287 s** | CC002, measured in `int8-calib-crops-wired.txt` |
| build (grids -> int8 weights, kernels bound) | **0.041 s** | |
| first call, Triton cache **warm** | **0.275 s** | |
| steady-state call (median of 5) | **0.0267 s** | the frame itself |
| first call, Triton cache **cold** | **2.531 s** | fresh `TRITON_CACHE_DIR`, compiled from scratch |

So the 6.56 s was almost entirely the **24 full-frame calibration** (24 x ~0.26 s = 6.2 s), which the crop
calibration removed; Triton's JIT was small in that block because the cache was already warm on this machine. A
user's first-ever run pays **2.53 s** of compilation, a re-render pays 0.28 s, and steady state is 0.027 s.

After the crop change the whole block reads 1.28 s (SC004): 0.29 calibration + 0.04 build + 0.28 first call, and
the remaining ~0.7 s is the first frame's own host work (buffer allocation, frame construction, the sanity check).

## Where the 9.79 s now sits

| block | seconds | what would move it |
|---|---|---|
| interpreter + CLI + ffprobe + CUDA init | 2.38 | imports; not touched |
| **decode 16 spread frames** | **4.69** | fewer frames, or sequential decode instead of seeking |
| probe calibration (crops) | 0.56 | done - was 12.6 |
| engine deserialize | ~0.5 | a smaller plan; not touched |
| body block (calibrate + build + first call) | 1.28 | Triton cache is already warm; cold adds 2.5 |

The decode is now the largest single item, and it is the same 4.69 s the probe pays to *find* frames it no longer
needs in full - a spread decode is only needed because calibration used to want variety.

## The certificate's 0.45%, separated by mechanism

`int8-certificate-removal.txt` left two candidates - the ~2 GB quantised twin's allocation, and the engine warm-up
the certificate performs - and said the discriminating experiment was an allocation-only perturbation. It now has
one, on the current tree, four arms in one session, 494 frames each, ffv1:

| arm against the shipped certificate-off path | worst share | frames above 0.1% | peak |
|---|---|---|---|
| certificate ON | **0.00057%** (frame 23) | 0 | 21 |
| 2 GB allocated and released, no certificate | **0.00000%** | 0 | **0** |
| fp16 engine warmed on 6 frames, no certificate | **0.00057%** (frame 23) | 0 | 21 |

**The allocation is bit-identical (peak 0, 0.00000%) and the warm-up reproduces the certificate's difference
exactly** - same worst frame, same peak, same share. So the mechanism is the engine warm-up, not the memory state.

And the 0.45% does not reproduce: on the current tree the certificate moves 0.00057%, three orders less than the
0.45050% of 2026-11-19, with 0 frames above the bar either way. Two things changed in between (the tail-CSC payload
and the crop calibration), and this page does not attribute the difference between 0.45% and 0.00057% to either -
it only states that the shipped path is 0.00057% from the certified one today, which is far inside the bar. **No
action needed on the certificate**, and the "shipped pixels are not the measured pixels" worry from the audit is
answered for the current tree.

## Reproduce

```bash

RVE_INT8_CALIB_CACHE=0 TRITON_CACHE_DIR=$(mktemp -d) python3 scripts/body_build_split.py   # cold cache
ARMS="off cert alloc warm" ARM_ENV_OFF="RVE_INT8_CERTIFY=0" ARM_ENV_CERT="RVE_INT8_CERTIFY=1" \
    ARM_ENV_ALLOC="RVE_DIAG_ALLOC_MB=2048" ARM_ENV_WARM="RVE_DIAG_WARM_ENGINE=1" \
    SINK=ffv1 ROUNDS=1 CLIPS="bd_violet20s.mkv" scripts/wall_ab.sh
PYTHONPATH=. python3 harness/scripts/startup_split2_records.py

    --records docs/wsp/verified/records/int8-startup-split2.jsonl --bars docs/claims-bars.json
```
