# Upscaling speed — the current measurement set

Written 2026-11-20. This page is a **view over records, not a new measurement**. Every value quotes a
record id; the files under `docs/wsp/verified/records/` are truth, and where this page and a record
disagree, the record wins. Numbers computed from records for readability are marked *derived*.
Prose that predates the harness (§4) is marked *prose, no record*.

Scope of everything below unless a row says otherwise: RTX 4060 Ti 16 GB (176 dense int8 TOPS,
288 GB/s, PCIe gen 3 x8), Ryzen 5 5600, TensorRT 10.12, torch 2.9; 1920x1080 -> 3840x2160; model
`2x-Futsuu-Anime(1).pth` (SRVGGNetCompact, 64 body channels, 18 convolutions); one GPU job at a time.

Two knobs decide which number applies, both shipping defaults: `--quality_preset best` = the fp16
engine, `fast` = the int8 body; `--temporal_reuse` = ON since 2026-11-20, with the correction.

## 1. The engine: int8 body against the fp16 engine

Product path (wall clock per frame, `hevc_nvenc` alongside, reuse off), one session
`s-2026-11-19T10:03:39+03:00`, rounds 2-3, arms interleaved, one process per arm, median:

| arm | ms/frame | fps *(derived, 1000/ms)* | record |
|---|---|---|---|
| fp16 engine | **52.59** | 19.0 | `int8-tail-csc.jsonl` : JC011 |
| int8 body | **31.54** | 31.7 | `int8-tail-csc.jsonl` : JC012 |
| ratio | **1.667406x** | | JC013 (*derived*, formula `JC011/JC012`) |

The same pair on a **null sink**: 52.39 / 31.47 ms = **1.66476x** (JC001 / JC003 / JC004, session
`s-2026-11-19T09:53:47+03:00`). The same run is also filed as ED001 / ED002 / ED007 in
`int8-encoder-delta.jsonl` — one draw, two files, do not count it twice. Encoder cost on this clip is
0.07-0.20 ms per arm *(derived: 31.54-31.47 and 52.59-52.39)*.

Population for both pairs: `bd_violet20s.mkv`, 494 frames, reuse off (`--no_temporal_reuse`).

Bars (`docs/claims-bars.json`): `bar_int8_wall` = **1.2x** (wall clock, median, n>=2) — 1.667x passes
with margin; `bar_int8_window` = 1.4x. The picture bar is a different number (`bar_int8_share` 0.1%
of pixels, worst frame) and is not traded here.

## 2. Where the int8 milliseconds are

`docs/FRAME-BUDGET.md`, generated by `harness/scripts/frame_budget.py` from the render log at commit
`948304a6`. 1920x1080 -> 4K, int8 body, null sink, app's own CUDA events:

| stage | ms | share | what it is |
|---|---|---|---|
| head | 0.60 | 2% | 3 -> 64 channels, fused with PReLU and with the quantisation into int8 codes |
| quantise | 0.00 | 0% | gone by construction — the head writes codes |
| hops | 24.50 | 94% | sixteen 64 -> 64 int8 3x3 convolutions, one Triton kernel launched sixteen times |
| tail | 1.00 | 4% | 64 -> 12 channels, pixel shuffle to 3 at 2x, residual add — one kernel |
| **BODY TOTAL** | **26.20** | 100% | |
| pack + queue | 2.06 | | the 12.44 MB 4K yuv payload over PCIe |
| **render loop** | **31.48** | | what the user waits for; `null` sink, no encoder |
| everything else | +3.22 | | reader, model-call wrapper, writer back-pressure |

Floors that bind it: the hops have a **13.9 ms** floor both at 176 TOPS (152.9 GFLOP x 16) and at
288 GB/s of DRAM (250.6 MB x 16) — the hop sits on the machine's ridge (611 FLOP/byte against 610).
The body is therefore **1.88x** its floor *(derived: 26.20/13.9)*, and the loop adds the pack
(1.9-2.4 ms, PCIe gen 3 x8 is a property of the motherboard) plus 3.22 ms of plumbing.

Consequence for any proposal: the remaining levers are **boundaries between operators** — fuse a hop,
delete a pass, move work off the PCIe link — not arithmetic. That is why int8/FP8 implicit, explicit
Q/DQ, width C=32/48, Winograd through cuDNN, activation sparsity, 3x3-into-5x5 and Strassen at N=64
are all closed by measurement rather than by opinion.

A millisecond is not worth the same everywhere: the bar is the ratio `R = fp16 / int8`, so
`dR/dI = R/I` for a millisecond taken out of the int8 body and `dR/dS = (F-I)/I²` for one taken out of
a stage both arms pay — the factor between them is **`F/(F-I)` = 52.59/21.05 = 2.50** *(derived from
JC011/JC012; 2.50 on the null-sink pair too)*. `FRAME-BUDGET.md` says "~2.8x" there and it does not
reproduce: 2.78 is `1.667²`, which is not what the derivative gives. No record carries either number —
both are derivations, and only the one above follows from the records.

## 3. The earlier window draw (older, GPU-event instrument)

36.19 ms = 27.63 fps (R002) against fp16 48.94 ms = 20.43 fps (R003), same session
`s-2026-11-17T03:18:17Z`, n=8, mean, gate off, no encoder. That draw read **1.35x**; an earlier one
read 1.41x, and the fp16 plan read 48.94-55.61 ms across that day's runs. Instrument: `torch.cuda.Event`
around whole-frame calls for int8 and around plan executions for fp16 — GPU events on both sides, but
not the same scope. Treat this pair as directional; the product number is §1 (wall clock + encoder).

## 4. Against the original 2.4.2 — *prose, no record*

Measured 2026-11-15, before the harness, and recorded only in `docs/PERFORMANCE.md` § Against the
original 2.4.2. Same clip, model and encoder, each side on its own defaults:

| clip | original 2.4.2 | now | ratio |
|---|---|---|---|
| Bebop 35 mm TV, 240 frames (1080p -> 2160p) | 27.73 s | 14.95 s | **1.85x** |
| anime, 498 frames, gate forced off | 53.94 s | 33.12 s | **1.63x** |
| anime, 498 frames, defaults (gate on) | 53.94 s | 12.51 s | 4.31x — **withdrawn** |

The 4.31x row is withdrawn: it multiplied the engine half by a gate half measured on a different
pipeline state. The engine half — optimization profile 3 -> 5, tiling default, the pipe and colour
fixes — is 1.63-1.85x and applies to every frame of every clip. On film the honest number is the
1.85x, because the gate refuses there (noise floor 2.27 against the 1.5 limit).

## 5. The reuse gate — on by default since 2026-11-20, with the correction

960 s cut, 201 frames, product encoder (`hevc_nvenc -cq 18`), fp16 engine, three interleaved rounds in
one session `s-2026-11-20T11:10+03`, records `docs/wsp/verified/records/reuse-decision-statistic.jsonl`:

| configuration | ms/frame | fps | record |
|---|---|---|---|
| gate OFF — every frame rendered | **51.45** | 19.4 | RU050 |
| gate ON — 124 of 201 frames reused (61.7%) | **26.01** | 38.4 | RU049 |
| gate ON + correction | 27.5 | 36.4 | RU050 note (*derived*) |

**1.98x**, and **1.87x** once the correction is charged. Through an `ffv1` lossless 4K sink the same
pair reads 58.46 -> 48.84 ms = 1.20x, because the fixed encode/convert cost dominates there — a number
about that sink, not about the product.

Correction cost inside the loop: **0.49 ms/frame**, 0.79 ms per reused frame (RU052 note; RU052 itself
is 40.26 ms/frame through `ffv1`, not comparable with the pair above). The standalone cost script
prices the correction at 2.428 ms over 50 iterations (RU032) — the loop pays less because it overlaps.

The shipped path was also verified for what it emits, not only for speed: 3 of 124 reused frames over
the 0.1% bar, worst 0.1977% (RU051), the same three frames as the lab, and every non-reused frame
bit-identical to the ungated render. **Those three were not solved later** — they were characterised and
accepted: `reuse-correction-limit` measures the remainder as the frame's own moving detail (no cheap
statistic separates it; the codec's motion field and a DIS flow both fail on the same frames), and
`reuse-residual-imperceptible` records the owner's judgement on the 1:1 crops, with VMAF (4K model) 100.0
on frames 16-22 for the correction. The product decision (`reuse-ships-on-with-correction`) ships it on
that basis, not on a clean bar.

Bounds: the auto tuner refuses material it cannot certify. On film and on noise the gate declines
(noise-floor limit 1.5), and the honest number is then the ungated fp16 one, ~51.45 ms/frame. Dense
moving line art is refused outright (noise floor 31.16, `reuse-motion-content.txt`).

Known inconsistency in the record layer: `reuse-correction-limit` still says in its scope "the gate
ships off by default". The product decision is `reuse-ships-on-with-correction` (ON, 2026-11-20) and
`backend/rve-backend.py --temporal_reuse` defaults to True; the stale sentence is prose, not a record.

## 7. What this page does not cover

- **One card, one model, one geometry.** Other GPUs untested; int8's advantage is a property of the
  card (external evidence, not measured here). 4x models have no throughput measurement — the 4x work
  is a correction/quality result.
- **The gate half is one clip**, a digital-BD anime cut the auto tuner certifies. There is no gate-ON
  measurement on film because the gate refuses there.
- **Same-session ratios only.** Run-to-run drift is ±15%, across sessions up to 26%; 45.7 ms and
  51.37 ms were the same engine in two sessions. Never divide one session's ms by another's.
- **n = 1 is a smoke test.** The window pair (§3) is one draw at n=8 with a split instrument.
- **Artifacts.** RU049/RU050/RU051/RU052 name logs under `~/rve-scratch/` (outside the repo, sha256 in
  the record); the int8 arm logs named by JC001-JC013 are in `docs/wsp/verified/logs/`.
