# The int8 frame is accounted for - and the profile line cannot be summed

Measured 2026-11-18 18:00-18:15 on BD Violet and the Chainsaw same-shot cut, reuse off, one run per arm
(`harness/scripts/wall_ab.sh`, null sink). The question came from `int8-wall-ab.txt`: the app's profile printed
"frame total 50.40 ms" against named parts summing to 44.17, and the 6.23 ms left over was 88% of what
int8 bought - so "where the frame goes" was unsafe to quote.

## What was missing was naming, not cost

Three stages ran inside the frame window and were never printed: the wrapper around the body call, the
preview payload, and the pinned-slot fill + `writeQueue.put`. They are now timed (`up_wall`, `preview`,
`pack`) and the line prints them next to `named` and `unaccounted`. Nothing was optimised; the 6.2 ms did
not shrink, it acquired a name.

| run | render loop | body phases | pack+queue | named | profile total | unaccounted |
|---|---|---|---|---|---|---|
| Violet fp16 | 58.84 | - | 3.79 | 59.32 | 59.05 | -0.27 |
| Violet int8 | 51.85 | 44.9 | 3.87 | 67.55 | 67.32 | -0.23 |
| Chainsaw fp16 | 58.81 | - | 3.80 | 59.21 | 59.03 | -0.18 |
| Chainsaw int8 | 46.53 | 38.6 | 3.52 | 59.10 | 58.94 | -0.16 |

So the leftover inside the profile is now zero to -0.3 ms (negative because `read wait` sits just outside
the frame window). **The 6.2 ms was ~3.8 ms of pack + queue and ~2.4 ms of the wrapper and read wait** -
both named in the ledger for the tiled fp16 path, neither printed here.

## The finding that matters more: the profile total is not wall time

On the int8 arms the profile's frame total runs **27-30% ABOVE the render loop's own wall clock**
(67.32 against 51.85 on Violet; 58.94 against 46.53 on Chainsaw), while on the fp16 arms the two agree to
0.3%. The cause is visible in the numbers: `model wall` reads 63.5 ms around a call that contains a
43.7 ms body - with pipelined inference `upscaleOption(frame)` blocks waiting for the frame already in
flight, so the per-iteration window contains overlapped work, and summing those windows counts it twice.

Consequences, and they are the reason this file exists:

- **For wall time, quote the render loop line, never the profile total.** `int8-wall-ab.txt` already does
  this (its records come from the loop), so its ratios stand.
- **For attribution, quote the body's phase counter** - which sums to the body and does not overlap.
- **A "frame budget" built by adding profile components is invalid on the int8 path.** It was probably
  already partly invalid on the gate path; there the gate serialises, so the error was small.

## Not explained here

`last_model_ms` (printed as "engine") reads 17.2-17.5 ms on the int8 arms of this session against 1.93 ms
in the 17:00 wall A/B, and the self-reported inference moved 43.90 -> 60.80 with the body's own phases
moving only 42.0 -> 43.7. That is an instrument question, not a body question, and it is NOT resolved
here: the two sessions were at the same clocks (2790 MHz) with no throttle reason active, and a repeat
run 10 minutes later reproduced it. Until it is explained, `self-reported` on the int8 path cannot be
compared across sessions either.

Also not covered: one machine, one run per arm (this is an attribution question, not a rate); no NVENC
arm; the gate is off, so the gate's own `get_frame_tensor` cost (2.80 ms in the ledger) is not exercised.
